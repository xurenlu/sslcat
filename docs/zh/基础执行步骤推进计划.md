基础执行步骤推进计划
====================

总体目标
--------
- 建立一套覆盖易用性、稳定性、高可用的持续改进闭环，明确评估标准、落实执行队伍、固化节奏。
- 在 6 个月内完成从现状盘点 → 快速增量 → 架构深度治理 → 持续运营的完整路径，为后续商业化提供稳定底座。

阶段划分与交付
--------------

### 阶段 1（0-1 个月）：现状评估与优先级梳理
- **目标**：掌握当前基础设施与产品体验痛点，建立量化基线。
- **关键任务**：
  - 组织跨部门访谈（产品、研发、客服、BD）收集痛点，形成《痛点原始记录》。
  - 拉通日志、监控、告警、客服系统导出原始数据，搭建数据看板雏形（Grafana/Looker/Metabase 等）。
  - 明确核心旅程（注册→集成→运营）并进行启发式评测 + 5 人快速可用性测试。
  - 梳理当前架构拓扑与容灾策略，列出单点风险清单。
  - 建立初版 SLI/SLO 草案（接口成功率、页面性能、可用性 SLA）。
- **产出物**：
  - 《可用性/稳定性/高可用现状报告》
  - 《优先级矩阵（KANO + 实施成本）》
  - 数据仪表（基础监控 + 客户旅程指标）
- **角色与资源**：PM（牵头）、Tech Lead（技术现状）、QA（测试设计）、运营（客户访谈）。
- **里程碑**：第 4 周完成评估会，确认 Top10 改进项与负责人。

### 阶段 2（1-3 个月）：快速收益与基础能力补齐
- **目标**：在不大幅改动架构的前提下，显著降低主诉痛点和显性故障。
- **关键任务**：
  - UI/交互快速迭代（布局、表单、配置向导），每两周用户评测一次。
  - 全链路监控补齐：接入链路追踪（Jaeger/Tempo），统一日志规范，设置告警阈值与 On-call 手册。
  - 搭建自动化测试框架（冒烟 + 回归 + 合规检查），纳入 CI，建立失败阻断机制。
  - 引入金丝雀发布流程，结合灰度流量开关，实现低风险上线。
  - 针对高频问题接口实现熔断、限流、降级策略。
- **产出物**：
  - 《快速收益行动清单（完成情况）》
  - 自动化测试覆盖率报告 & CI/CD 流程图
  - On-call 手册 & 值班排班表
- **角色与资源**：设计（UI）、前后端工程师、SRE/DevOps、QA、数据分析。
- **里程碑**：第 8 周完成第一次金丝雀上线回顾；测试覆盖率较阶段 1 提升 30%。

#### 已完成里程碑（2025-10-29）
- **表单体验再设计**：首次设置向导引入密码强度指引、实时校验与错误聚合提示，默认禁用提交流程直至满足安全策略。
- **后端合规校验**：`handleFirstTimeSetup` 增加长度/复杂度校验、域名与目标地址一致性验证，同时将关键结果写入 Prometheus 新增的 `sslcat_first_setup_events_total` 计数。
- **测试能力搭建**：落地 Vitest + Testing Library 单元测试框架（新增 `test:unit` 脚本），覆盖首设向导核心交互，输出 `frontend/tests/unit/FirstTimeSetup.test.tsx`。
- **配置同步**：新增 `vitest.config.ts`、`setupTests.ts` 和 TypeScript 配置，以便纳入 CI；后续可在 release workflow 中串联。

#### Go 测试修复行动项（待执行）
- **现状**：运行 `go test ./...` 时，`internal/cache`、`internal/config`、`internal/webp` 及 `tools` 目录存在历史遗留失败（MIME 判定、配置校验、重复 `main` 等）。
- **优先计划**：
  1. `internal/cache`：补齐 MIME/Content-Type 映射，确保 JSON/CSS/JS 被判定为缓存命中类型，并更新对应单测预期。
  2. `internal/config`：梳理测试用例中的默认配置，提供合法端口与 SSL 邮箱，避免触发校验失败；必要时拆分“失败用例”与“成功回滚”测试逻辑。
  3. `internal/webp`：检查 `Converter` 方法重复声明，拆分或调整构造函数，保持 API 兼容的同时通过单测。
  4. `tools`：将多 `main` 脚本改造为 build tag 或子命令形式（例如 cobra/viper），或调整测试策略仅编译目标脚本，避免重复声明导致的 `go test` 失败。
- **时序建议**：先以 1 周完成 `internal/cache`/`internal/config` 快速修复；随后用 1-2 周治理 `internal/webp` 与 `tools`，最后将 `go test ./...` 纳入 CI 必跑项目。

### 阶段 3（3-6 个月）：架构升级与多活改造
- **目标**：解决结构性瓶颈，提高容错与扩展能力。
- **关键任务**：
  - 数据库分层治理（读写分离、分库分表或多租户隔离），完善备份与演练。
  - 服务治理：拆分重负载服务，接入服务网格或统一治理框架（熔断、限流、路由）。
  - 多可用区部署：实现主备或多活，完善流量调度与一致性校验。
  - 引入容量自动化（HPA/自研伸缩策略），建立容量预测模型。
  - 建立“Game Day”演练流程，每月演练一次（故障注入、恢复时长评估）。
- **产出物**：
  - 《架构升级设计说明》
  - 多活/容灾演练记录 & RTO/RPO 结果
  - 容量规划与成本分析报告
- **角色与资源**：架构师、DBA、SRE、后端工程师、财务/成本控制。
- **里程碑**：第 20 周完成首轮多活演练并达标；容量预测误差 <15%。

### 阶段 4（6 个月后持续）：持续运营与优化
- **目标**：将改进流程标准化、制度化，形成可持续运营机制。
- **关键任务**：
  - 建立季度技术评审会（跟踪 SLO、Error Budget、客户反馈、商业指标）。
  - 维护改进 Backlog 与 OKR 对齐，确保每季度有明确重点项目。
  - 引入 AIOps/异常检测辅助运维，持续优化告警噪音与响应效率。
  - 构建客户声音闭环：用户社区、定期客户访谈、客服 FAQ 自动化。
- **产出物**：
  - 季度评审纪要 & 行动项跟踪表
  - OKR 对齐文档 + KPI Dashboard
  - 客户成功指标（续费率、扩容率、CSAT）分析
- **角色与资源**：管理层、产品运营、SRE、客户成功团队、数据团队。
- **里程碑**：每季度形成《技术运营白皮书》并存档。

短期执行节奏（前 12 周）
--------------------
- 第 1-2 周：资料收集、访谈、数据接入；完成初版指标基线。
- 第 3-4 周：现状报告草案 + 优先级矩阵；召开阶段 1 评审会。
- 第 5-6 周：启动 UI 快速迭代与监控补齐；CI 自动化测试框架上线。
- 第 7-8 周：落地金丝雀流程并完成首次上线复盘；发布 On-call 手册。
- 第 9-10 周：实现首批熔断/降级策略；监控指标稳定运行。
- 第 11-12 周：阶段 2 回顾会议，沉淀最佳实践并为阶段 3 做预算与资源申请。

指标与验证机制
--------------
- **易用性**：任务完成时间、错误率、NPS、可用性测试成功率。
- **稳定性**：P0/P1 事故次数、MTTR、自动化测试通过率、金丝雀回滚率。
- **高可用**：SLA 达成率、Error Budget 消耗、RTO/RPO、容量利用率。
- 每月形成《指标盘点报告》，对偏差项目提出纠偏方案。

协同与治理
----------
- 设置跨部门 Steering Committee，双周跟进行动项。
- 采用项目管理工具（如 Jira/飞书 OKR）记录任务进度与风险日志。
- 关键风险（人力不足、预算延迟、技术未知）需在阶段评审会上复盘与升级。
